# week-palner

Однофайловый недельный планировщик задач с опциональной синхронизацией через
Supabase. Полная спецификация: [docs/spec.md](docs/spec.md). Инструкция по
подключению Supabase и деплою: [README.md](README.md).

## Архитектура

- `index.html` — всё приложение (HTML + CSS + JS), один файл, без сборки,
  без npm, без фреймворков. `supabase-js` подключается как ES-модуль прямо
  с CDN (`https://esm.sh/@supabase/supabase-js@2`) через `<script type="module">`.
- **В репозитории нет никаких данных** — ни ролей, ни задач, ни плана. При
  первом открытии палитра пуста. Роли/задачи/план грузятся одним JSON-файлом
  через кнопку «Импорт JSON» (формат — см. README.md) и сохраняются в
  `localStorage` браузера (`week-planner-roles` — роли, `plan-<WEEK>` — план).
- `supabase/schema.sql` — таблицы `plans` (план) и `role_configs` (роли и
  задачи, одна строка на пользователя), RLS-политики, общий триггер
  `updated_at`. Прогоняется вручную в SQL Editor Supabase, миграций нет. При
  входе синхронизируется и план, и роли — на новом устройстве достаточно
  войти тем же email, повторный импорт JSON не требуется.
- Local-first: `localStorage` — основное хранилище, Supabase — необязательный
  слой синхронизации поверх. Приложение обязано полностью работать офлайн и
  без аккаунта.

## Важные инварианты (не ломать без явного запроса)

- Один файл `index.html`. Не разносить на модули, не переписывать на
  React/Vue/что-либо ещё, не добавлять сборку.
- **Никаких личных данных в репозитории** — не коммитить роли, задачи или
  план (ни как JSON-файл, ни захардкоженными в JS). Это касается и истории
  git: если такие данные случайно попали в коммит, требуется переписать
  историю и форс-пуш, а не просто удалить файл новым коммитом.
- Формат экспорта/импорта JSON — обратная совместимость: старое поле `blocks`
  (`task/name/role/day/date/minutes/hours`) не менять, `roles` — аддитивное
  поле поверх него.
- В клиентском коде — только `anon` ключ Supabase. `service_role` ключ
  никогда не коммитится и не используется в браузере.
- Все вызовы Supabase — в try/catch; сетевая ошибка не должна ломать
  локальную работу приложения.

## Локальный запуск

Файл можно открыть напрямую (`file://`) — сетевых запросов при старте больше
нет (роли/план грузятся через `<input type=file>`, не `fetch`). Для проверки
Supabase-синхронизации сеть нужна в любом случае.

```bash
python3 -m http.server 8000   # опционально, для проверки как на GitHub Pages
```

## Как проверять изменения

Ручное тестирование в браузере (импорт JSON, drag-and-drop, localStorage,
Supabase-сессии) — автотестов в проекте нет. Чек-лист для ручной проверки —
в конце [docs/spec.md](docs/spec.md) и [README.md](README.md).

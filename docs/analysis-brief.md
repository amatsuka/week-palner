# Бриф для анализа производительности

Документ для отдельной сессии, которая будет разбирать данные недельного
планировщика. Здесь: что именно измеряет инструмент, в каком виде лежат
данные, как их достать и чего по ним считать **нельзя**.

Код инструмента — [../index.html](../index.html), полная спецификация
поведения — [spec.md](spec.md).

## Что это за инструмент

Недельный планировщик нагрузки по **ролям**. Пользователь заранее раскидывает
по дням недели блоки работы, а потом отмечает, сколько по каждому реально
отработал получасовыми отрезками (pomodoro).

Ключевое для интерпретации:

- **«Задача» здесь — это тип работы, а не конкретное дело.** `Разработка игры`,
  `Кайт-сессия`, `Занятие по языку` — это категории, сгруппированные по ролям
  (`Разработчик-предприниматель`, `Инструктор по кайт-серфингу`, …). Конкретные
  дела живут в другом месте (Notion) и сюда не попадают. Поэтому нельзя считать
  «сколько задач выполнено» — измеряется **распределение внимания и времени по
  направлениям жизни**, а не закрытие тикетов.
- **Времени начала нет вообще.** Блок — это «в этот день столько-то часов на
  эту тему», без привязки к часам. Порядок блоков внутри дня — это порядок,
  который пользователь сам задал перетаскиванием (намерение), а не хронология
  выполнения.
- Всё кратно **30 минутам**. Разрешающая способность данных — полчаса.

## Модель блока

Один блок («карточка») в массиве `items`:

```js
{ id: "block-…", task: "dev-game", day: 0, min: 90, did: 30, done: false }
```

| поле | смысл |
|---|---|
| `id` | идентификатор карточки; в одном дне может быть несколько карточек одной задачи |
| `task` | id типа задачи, разрешается через конфиг ролей |
| `day` | `0..6` — пн..вс, **`-1`** — столбец «Без дня» (надо на неделе, день не выбран) |
| `min` | **запланировано**, минут (кратно 30) |
| `did` | **отработано**, минут (кратно 30); может превышать `min` — переработка |
| `done` | ручная галочка «выполнено», ставится пользователем |

Роли и задачи хранятся отдельно от плана:

```js
{ roles: [ { id:"r1", name:"Разработчик-предприниматель", color:"var(--r1)",
             tasks:[ {id:"dev-game", name:"Разработка игры"}, … ] } ] }
```

В плане роли нет — только `task`; принадлежность роли восстанавливается по
конфигу ролей. Поэтому для анализа нужны **оба** куска данных.

## Где лежат данные

Недели независимы: на каждую — своя запись. Кода недели в формате ISO
(`2026-W37`), понедельник этой недели — в поле `start`.

1. **localStorage браузера** — основное хранилище.
   - `plan-<WEEK>` → `{ items: [...], updatedAt: "ISO" }`
   - `week-planner-roles` → `{ roles: [...], updatedAt: "ISO" }`
2. **Supabase** (если пользователь входил в аккаунт) — те же данные:
   - таблица `plans`: `user_id, week, items (jsonb), updated_at`, уникально по `(user_id, week)`
   - таблица `role_configs`: `user_id, roles (jsonb), updated_at`, одна строка на пользователя
3. **Экспорт JSON** — кнопка «Экспорт JSON» выгружает текущую неделю файлом
   `plan-<дата понедельника>.json`.

### Как выгрузить всё разом

Из консоли браузера на странице планировщика (`copy()` кладёт в буфер):

```js
copy(JSON.stringify({
  roles: JSON.parse(localStorage.getItem("week-planner-roles") || "null"),
  weeks: Object.keys(localStorage)
    .filter(k => k.startsWith("plan-"))
    .map(k => ({ week: k.slice(5), ...JSON.parse(localStorage.getItem(k)) }))
}, null, 2))
```

Из SQL-редактора Supabase:

```sql
select week, updated_at, items from public.plans order by week;
select roles from public.role_configs;
```

### Формат файла экспорта

```jsonc
{
  "version": 2,
  "week": "2026-W37",
  "start": "2026-09-07",        // понедельник недели
  "days": 7,
  "mode": "pool",
  "roles": [ /* конфиг ролей целиком, см. выше */ ],
  "blocks": [
    {
      "task": "dev-game",
      "name": "Разработка игры",              // имя задачи
      "role": "Разработчик-предприниматель",  // имя роли, не id
      "day": 0,
      "date": "2026-09-07",                   // null для «Без дня» (day: -1)
      "minutes": 90,                          // запланировано
      "hours": 1.5,                           // то же в часах
      "worked": 30,                           // отработано, минут (в часах поля нет)
      "done": false
    }
  ]
}
```

Отличия от внутреннего формата: `min` → `minutes`, `did` → `worked`, добавлены
человекочитаемые `name`/`role`/`date`, `id` карточки не выгружается. Порядок
элементов `blocks` = порядок карточек внутри дня.

## Как считает сам интерфейс

Чтобы цифры анализа сходились с тем, что пользователь видел на экране:

- «За неделю» = сумма `min` по блокам **с днями 0..6** (склад `day: -1` не входит).
- «Загруженных дней» = число дней, где сумма `min` больше нуля.
- «В среднем» = неделя / загруженные дни, округлённое до 30 минут.
- «Без дня» показывается отдельной суммой и в недельную нагрузку не входит.
- День подсвечивается как перегруженный при сумме `min` **больше 480 минут** (8 ч).
- Прогресс-заливка карточки = `did / min`, обрезанная сверху на 100%.
- Счётчик «Nд» у задачи в палитре = число **дней**, где она встречается
  (не число карточек), и склад в него не входит.

## Подводные камни (читать до первых выводов)

1. **Истории нет.** На неделю — одна запись, которая перезаписывается целиком.
   `updated_at` — время последней правки всей недели, у карточек собственных
   меток времени нет. Нельзя узнать, *когда* именно отмечался отрезок или
   менялся план. Если пользователь несколько реальных недель работал на одном
   и том же коде недели, ранние состояния затёрты — данных за «пару недель»
   в этом случае физически нет, есть финальный снимок.
2. **`min` правится задним числом.** Запланированное время можно изменить в
   любой момент, в том числе после выполнения, и прошлое значение нигде не
   хранится. Поэтому «точность оценки» по `min` vs `did` достоверна, только
   если пользователь подтвердит, что план после начала недели не трогал.
3. **Перенос остатка искажает `min == did`.** Перетаскивание с Option
   отщепляет недоделанное: в исходной карточке `min` становится равным `did`,
   а остаток уезжает отдельной карточкой. То есть `min == did` часто означает
   не «идеально оценил», а «перенёс остаток». Признак переноса — парная
   карточка того же типа задачи с `did: 0`.
4. **`done` не связан с `did`/`min`.** Это ручная галочка в конце дня. Бывает
   `done: true` при `did: 0` (отметил, но отрезки не считал) и `done: false`
   при `did >= min` (сделал, но не отметил). Как метрика выполнения — слабый
   сигнал; считать по `did`.
5. **`did` — самоотчёт, а не таймер.** Отрезки проставляются кнопками, обычно
   в конце дня по памяти. Ожидаемы округление в большую сторону и пропуски.
6. **Карточки несопоставимы между ранними и поздними неделями.** Раньше
   повторный сброс задачи в день **увеличивал** существующий блок (склейка),
   сейчас создаёт отдельную карточку. Поэтому «число карточек» между неделями
   сравнивать нельзя — сравнивайте минуты.
7. **Склад `day: -1` — это намерение без даты.** Он не входит в дневную
   нагрузку. Что осталось в нём к концу недели — отдельный интересный сигнал
   (запланировал, но так и не поставил в день), но не смешивайте его с
   выполненной или распределённой работой.
8. **Идентичность задач держится на конфиге ролей.** Сравнение по неделям
   возможно, пока `task.id` стабильны. Если роли переимпортировались JSON-ом с
   другими id, ряды по неделям разъедутся — сверяйте по `id`, а расхождения
   ловите по `name`.
9. **Переработка допустима.** `did > min` — нормальное состояние, не ошибка
   данных. При суммировании «выполнено» не обрезайте `did` по `min`.

## На какие вопросы данные отвечают

Разумно: как распределено запланированное и отработанное время по ролям и
дням; где систематически планируется больше, чем делается; насколько
равномерна нагрузка по дням недели; какие направления регулярно вытесняются;
сколько оседает в «Без дня»; доля переработок.

Не отвечают: во сколько и в каком порядке шла работа в течение дня;
длительность отдельных сессий; сколько конкретных дел закрыто; что происходило
между отметками; динамика внутри недели (есть только итоговое состояние).

# Спецификация: синхронизация недельного планировщика через Supabase

Статус: реализовано (см. [index.html](../index.html), [supabase/schema.sql](../supabase/schema.sql)).

## Контекст

Однофайловый веб-планировщик `index.html` (ванильный JS, без сборки, без
зависимостей, хостится на GitHub Pages). Хранит недельный план задач,
сгруппированных по ролям и раскиданных по 7 дням недели. Каждая запись —
задача + день + объём в минутах, без привязки ко времени начала.

Роли и задачи не хардкодятся в JS и не хранятся в репозитории — это личные
данные пользователя. Заводятся кнопками «+ Добавить роль» / «+ задача» прямо
в палитре, либо одним JSON-файлом через «Импорт JSON» (вместе с планом), и
сохраняются в `localStorage` браузера (`week-planner-roles`). При первом
открытии страницы палитра пуста.

До этой задачи план хранился только в `localStorage`, из-за чего на ноутбуке
и на телефоне получались два независимых плана (был костыль — кнопка
«Ссылка на план», упаковывающая состояние в hash URL).

Модель данных в коде:

```js
items = [ { task: "dev-game", day: 0, min: 90 }, ... ]
```

`task` — стабильный строковый id из импортированного набора ролей, `day` — 0..6 (пн..вс),
`min` — объём в минутах, кратный 30.

## Цель

Синхронизация плана между устройствами через Supabase, при сохранении
однофайловой архитектуры и работы офлайн. Открыл на телефоне — увидел то же,
что накидал на ноутбуке.

## Требования

### Архитектура

- Один файл `index.html`. Никакого бандлера, npm-скриптов и фреймворков.
  `supabase-js` подключается как ES-модуль с CDN (`https://esm.sh/@supabase/supabase-js@2`).
- **Local-first.** `localStorage` остаётся основным хранилищем: приложение
  полностью работает без сети и без входа в аккаунт. Supabase — слой
  синхронизации поверх, а не замена.
- Никакого своего бэкенда.

### База данных

Таблица `plans` (план):

| колонка | тип | примечание |
|---|---|---|
| id | uuid | pk, default `gen_random_uuid()` |
| user_id | uuid | references `auth.users(id)`, default `auth.uid()` |
| week | text | код недели ISO, например `2026-W37` |
| items | jsonb | массив `{task, day, min}` |
| updated_at | timestamptz | default `now()`, обновляется триггером |

- Уникальный индекс по `(user_id, week)` — на неделю одна строка, пишем `upsert`.

Таблица `role_configs` (роли и задачи — палитра):

| колонка | тип | примечание |
|---|---|---|
| id | uuid | pk, default `gen_random_uuid()` |
| user_id | uuid | references `auth.users(id)`, default `auth.uid()`, **unique** |
| roles | jsonb | массив ролей, как в JSON-импорте (`{id,name,color,tasks}`) |
| updated_at | timestamptz | default `now()`, обновляется триггером |

- `user_id` уникален — одна строка на пользователя (роли не зависят от недели).
- Обе таблицы: RLS включён, политики select/insert/update/delete —
  `auth.uid() = user_id`.
- Схема лежит в `supabase/schema.sql`, прогоняется в SQL-редакторе Supabase.

### Авторизация

- Supabase Auth, magic link по email. Без паролей.
- `redirectTo` — URL страницы на GitHub Pages, задан в блоке `CONFIG` в начале `index.html`.
- Без сессии приложение работает как обычно, локально, и показывает кнопку «Войти».

### Логика синхронизации

Роли (`role_configs`) и план (`plans`) синхронизируются независимо друг от
друга, по одинаковой схеме, каждый — своей парой local-storage-ключ +
таблица:

- При старте: сначала мгновенно отрисовывается локальное состояние, затем,
  если есть сессия, подтягиваются обе строки с сервера (сначала роли, потом
  план — так драг-дроп сразу видит актуальную палитру).
- Разрешение конфликта — last write wins по `updated_at`. Рядом с локальными
  данными хранится время последней синхронизации (`localStorage`: план —
  ключ `plan-<WEEK>`, поле `updatedAt`; роли — ключ `week-planner-roles`,
  тоже поле `updatedAt`). Если серверная версия новее — локальная
  подменяется, показывается уведомление («План обновлён…» / «Роли и задачи
  обновлены…»). Если локальная новее — заливается на сервер.
- Запись на сервер — дебаунс 800 мс после последнего изменения (отдельные
  таймеры для плана и для ролей).
- Синхронизация при загрузке страницы, при возврате вкладки в фокус
  (`visibilitychange`) и при восстановлении сети (`online`).
  Realtime-подписка на изменения таблиц — не реализована, вынесена как
  возможное будущее улучшение.
- Все сетевые вызовы обёрнуты в try/catch. Упавшая сеть не ломает UI: план и
  роли продолжают работать локально, индикатор показывает «Офлайн» или
  «Ошибка синхронизации».

### Интерфейс

- В верхней панели индикатор состояния: `Войти` (кнопка, когда нет сессии) /
  `Синхронизировано` / `Сохраняю…` / `Офлайн` / `Ошибка синхронизации`.
  Одна строка, без модалок.
- Кнопка выхода рядом с email пользователя.
- В палитре — инлайн-формы «+ Добавить роль» (имя + `<input type=color>`) и
  «+ задача» (имя, внутри роли) вместо модалок; сохранение по кнопке или
  Enter. Удаления/переименования ролей и задач в UI нет — только через
  экспорт → правку JSON → импорт.
- Остальной UI не менялся: пулы дней, drag-and-drop, подсветка одинаковых
  задач, экспорт и импорт JSON, кнопка «Скопировать план».

### Совместимость

- Формат экспорта JSON (`version: 2`, поля `task/name/role/day/date/minutes/hours`)
  не менялся, импорт старых файлов продолжает работать.
- Поле `week` заложено в схему сразу, хотя UI пока показывает одну неделю
  (`CONFIG.WEEK`). Переключение недель — следующая задача, текущая структура
  не должна ей мешать.

## Чего не делать

- Не коммитить Secret key (`service_role`). В клиенте только Publishable key
  (бывший `anon`) — публичный по дизайну, безопасен ровно при работающем RLS.
- Не создавать демо/дефолтные данные плана в коде и не коммитить их в
  репозиторий — роли, задачи и план импортируются пользователем через
  Импорт JSON, а не хардкодятся в JS и не лежат файлом в репо.
- Не переписывать планировщик на React, не разносить на модули.
- Не добавлять аналитику, трекинг и сторонние скрипты кроме `supabase-js`.

## Результат

1. `index.html` с синхронизацией плана и ролей.
2. `supabase/schema.sql` — таблицы `plans` и `role_configs`, индексы,
   RLS-политики, общий триггер `updated_at`.
3. `README.md` — как создать проект в Supabase, где взять URL и Publishable key,
   куда их вписать, как прогнать схему, как настроить redirect URL и как
   задеплоить на GitHub Pages.
4. Конфиг вынесен в начало `<script>` в `index.html` отдельным блоком `CONFIG`.

## Проверка

- [ ] Без входа приложение работает как раньше, план и роли переживают перезагрузку.
- [ ] После входа план и роли заливаются на сервер, строки в `plans` и
      `role_configs` появляются.
- [ ] Вход с другого устройства тем же email подтягивает тот же план и те же
      роли (без повторного импорта JSON).
- [ ] Изменение на устройстве A видно на устройстве B после перезагрузки
      или возврата вкладки в фокус.
- [ ] Выключенная сеть: правки не теряются, уходят на сервер после восстановления.
- [ ] Чужой пользователь не видит и не может изменить мои строки (проверить
      RLS запросом с другой сессией).
- [ ] Экспорт и импорт JSON работают как прежде.
